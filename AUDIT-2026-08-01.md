## Executive summary

NARUKAMI is a genuinely well-built single-user tool with a documentation problem that has become a correctness problem: the comments in this repo are unusually detailed and unusually often describe intent rather than behavior — statsLan says it "404s everything else" while serving your whole SPA dir pre-auth on 0.0.0.0, index.ts says handing the master token to a LAN device is "critical" to prevent while deciding loopback-ness from a client-supplied Host header, and the schema documents a 10-day retention policy for a table no code touches. The architecture is sound and the security primitives (constant-time compare, share-token scoping, path containment, env denylisting) are done properly; the failures are all at the seams between two layers. Three things bite you in ordinary daily use: pinned dock tabs silently lose their history to the retention sweep (measured: 7 of your 9 pinned runs are already blank), the header rate-limit meter is frozen because NARUKAMI sessions write usage-live.json to the embedded god home while /api/vitals reads the native one, and your determinism layer fails open on 86-98% of SubagentStop events so delegated edits are gated by neither hook. Nothing mechanical checks any of this — no CI, no git hooks, no root `npm test`, no lint, no coverage — which is exactly why a cwd-coupled test can sit on the branch producing a phantom "3 failing tests" signal and 2,400 lines of dead frontend code can survive two feature removals.

## Cross-cutting themes

_The systemic patterns behind the individual findings — the part a flat list cannot show._

### 1. The comment is the spec, and the code disagrees with it

This is the single highest-signal pattern in the audit, and it is dangerous precisely because the comments are good enough to be trusted. statsLan.ts:16-19 promises it "404s everything else — no HTML" while lines 197-203 serve any file under frontendDir before the 401 at line 206. index.ts:216-220 says handing the master token to a LAN device "is critical" to prevent, then decides via a forgeable header. godclaude.ts:169-171 promises an uninstalled layer "changes nothing about spawned sessions (fail-open)" while an inherited DET_HOOKS_HOME survives cleanEnv. runs.ts:222-224 says stopRun before respawn prevents EADDRINUSE, but node-pty's Windows kill is deferred. files.ts:382-384 justifies async per-file I/O one line after a fully synchronous walkAllFiles. block-unverified-completion.js:231-233 justifies its SubagentStop fail-open with "the parent's own Stop gate re-judges the whole turn" — verified false, because a subagent's Write/Edit never appears in the parent transcript. schema.prisma:93-95 documents a retention policy for a model with zero code references. Practical consequence: any future audit, agent, or you-in-six-months reading this codebase will be misled at exactly the points that matter most. Treat every guarantee-shaped comment as an untested assertion and convert the load-bearing ones into tests.

### 2. Trust derived from what the client says, not from where the connection came from

Every boundary failure in this audit is the same mistake. auth.ts:126-127 decides "is this local" from `req.headers.host.split(':')[0]`; ws.ts:150 does the same for Origin and Host; lanRelay.ts:109-110 is a raw `client.pipe(upstream)` that never rewrites headers, so a non-browser LAN client chooses those values freely. Meanwhile the socket already knows the truth — relayPeerAddress(req.raw.socket.remotePort) returns non-null for every relayed connection and is already used at share.ts:106 purely for device labelling. The second half of the same pattern is the token itself: frontend/api.ts:56 falls back to `import.meta.env.VITE_RUNNER_TOKEN`, so Vite inlines the master secret as a string literal into a bundle that both @fastify/static (index.ts:208-210, past the hook that returns early for non-/api URLs) and the statsLan listener serve without auth. One deliberate gate protects the injected copy while an identical copy sits in a file served to the same client. Fix the class, not the instances: derive locality from the socket, and never let a build emit a token.

### 3. Bounded in memory, unbounded in the database

The runner is disciplined about memory — MAX_TRANSCRIPT_CHARS = 2_000_000 (runner.ts:119), BATCH_MAX_CHARS, capTranscript, and terminals.ts:82 computes a 64 KB read window with a comment explaining why. Every path that goes through Prisma then loads everything: ws.ts:321-333 `include: { logs: { orderBy: { ts: 'asc' } } }` with no take (measured 1,390,804 bytes for one pinned run, sent as a single frame), terminals.ts:90-97 repeats the identical bug in the file cited as the counter-example, runs.ts:298-309 serializes an entire transcript to deliver one UUID on every Claude tab mount, workspace.ts:24 returns every AppSetting row (15 eodDigest blobs, ~51 KB, vs one 568-byte key the UI reads), eod.ts:407 returns every report's full markdown, and telemetry.ts:419 blocks the event loop for a measured 2,318 ms with synchronous readdirSync/readFileSync. The in-memory cap is the proof that the author knows the right answer; it just was never applied on the other side of the ORM.

### 4. Two homes, two sources of truth — the determinism layer is itself non-deterministic

The embedded GODCLAUDE design (DET_HOOKS_HOME → ~/.narukami/godclaude) is right, but the split was applied to writers and not to readers, and the seams now contradict each other. argus.ts:221-228 readUsage() reads os.homedir()/.claude/usage-live.json with no embedded-home parameter — unlike tailLog, which does take a baseDir — while godmode-statusline.mjs:69 writes to ${DET_HOOKS_HOME}/.claude/usage-live.json, which NARUKAMI sets on every pty (runner.ts:65), analyzer run and broker shell. On disk right now those two files are a full day apart with different numbers, and the always-visible header meter (HeaderCluster.tsx:125) shows the stale one. Same shape elsewhere: the global Disarm button removes only the global sentinel while session overlays keep sessions armed and the badge reads DORMANT; nativeWiring() never reads the native install's version, so NARUKAMI terminals silently run 1.7.2 modes and contract text while native terminals run whatever you upgraded to; and the health/stats caches are module-level and unkeyed by god home. The layer whose entire purpose is that behavior is the same every time has a bifurcated state root.

### 5. Nothing mechanical checks anything — including the checker

There is no CI workflow, no .github dir, no git hooks (core.hooksPath unset, .git/hooks has only samples), no root `test` script (`npm test` errors with Missing script), no eslint/prettier/biome in any package.json, and no coverage provider in either vitest config. packages/desktop is also excluded from the root typecheck. The direct cost is already visible: the branch's only red signal is a test that resolves its fixture from process.cwd() (files.search.test.ts:7) rather than a product bug; stage.mjs:40 prints `prisma engine present: false` and exits 0 so a broken installer packages cleanly; five LAN-dependent tests silently self-skip; and routes/runs.ts — the sole HTTP entry point to UAC elevation — plus the broker's connect-back handshake have zero tests, so removing the `p.runId !== msg.runId` clause or widening the shell ternary leaves all 483 tests green. The recursive version of this is the sharpest finding in the audit: your own determinism layer reports 26% of its decisions as fail-opens (110 'subagent transcript not found' + 14 'no transcript path' out of 472) and its self-improvement engine has rules for eight other conditions and none for a fail-open, so it never tells you it enforced nothing.

### Tier 1 — Fix now  <sub>(3)</sub>

_Confirmed correctness / security / data-loss issues that bite in ordinary daily use._

#### 1. Retention silently empties pinned dock tabs — 7 of your 9 are already blank

`packages/backend/src/services/runner.ts:717` · **trivial** effort · **CONFIRMED** · dimension: `data-loss`

**Why**  
pruneOldRunLogs deletes `where: { run: { endedAt: { lt: cutoff } } }` with no dockOpen exclusion, while schema.prisma:54 defines dockOpen as "is this an open tab in the workspace (restored on reopen)" — the two policies contradict each other and nothing reconciles them. ws.ts:332-333 does `const history = run.logs.map(l => l.chunk).join(''); if (history) send(...)`, so an emptied run sends NO data frame at all and the tab restores completely blank with no explanation. I measured your live desktop DB this session (AppData/Roaming/desktop/narukami.db, node:sqlite): of the 9 runs with dockOpen=1, SEVEN have zero RunLog rows — cmrhmnhrm00 (claude, 2026-07-12, ran 4h40m), cmrhmvw1r00, cmriha14z00, cmrioaxdf03 (killed), cmrj0z2ir00 (ran 14h), and two 'command' runs. Only the two July-29/Aug-1 runs still have logs (24 rows / 3,155 rows). This is already happening, not hypothetical, and it is the only data-loss finding in the audit. Raised by data-perf; the same unbounded-replay path was independently flagged by runner-pty.

**What to do**  
Change the sweep to `where: { run: { endedAt: { lt: cutoff }, dockOpen: false } }`. Because that removes the only bound on a pinned run's history, land it together with item 4 (capped replay) — otherwise a long-lived pinned tab grows without limit. Optionally, in the same boot sweep, flip dockOpen:false on any run whose logs were just deleted so it stops restoring as an empty tab, and have ws.ts emit a `[history older than 14 days was pruned]` marker when the Run row exists but has no logs.

#### 2. LAN client forging Host: 127.0.0.1 through the share relay is handed the master token

`packages/backend/src/index.ts:222` · **small** effort · **CONFIRMED** · dimension: `security`

**Why**  
index.ts:221-222 is `reply.type('text/html').send(isLoopbackHost(req.headers.host) ? injected : rawHtml)` — the decision to inject `window.__NARUKAMI__={token}` reads ONLY a client-supplied header. auth.ts:126-127 is `const name = h.split(':')[0]; return name === '127.0.0.1' || name === 'localhost';`, and lanRelay.ts:109-110 is `client.pipe(upstream); upstream.pipe(client);` — a raw byte pipe that never rewrites headers (its own docstring at line 12-13 says so). index.ts:178 (`if (!req.url.startsWith('/api')) return;`) skips requireAuth for `/`, so nothing else intervenes. The auditor ran a PoC composing the repo's OWN compiled dist/auth.js + dist/services/lanRelay.js with the index.ts wiring verbatim over a real LAN socket: an honest phone gets the raw HTML, a `curl -H 'Host: 127.0.0.1'` from the LAN gets the injected 64-hex master token, and replaying that bearer at /api/projects over the same relay returns 200. That token reaches POST /api/projects/:id/shell {admin:true}, i.e. an interactive PowerShell plus the UAC broker. The verifier independently re-derived the whole chain from source and confirmed the only caller passing frontendDir is desktop/src/main.ts:94, whose RUNNER_TOKEN_FILE (main.ts:72) is that instance's LIVE token. Precondition is one active share — the flagship mobile feature, not an unusual state.

**What to do**  
Stop deriving locality from the Host header once the relay is up. `relayPeerAddress(req.raw.socket.remotePort)` already returns non-null for every relayed connection (share.ts:106 uses it for device labelling): gate injection on `const viaRelay = relayPeerAddress(req.raw.socket.remotePort) !== null` and send rawHtml whenever viaRelay is true, regardless of Host. Apply the same viaRelay check in ws.ts before granting isMaster, so a forged `Origin: http://127.0.0.1` plus a lifted token can't open a terminal. Add a regression test that drives the real relay with a forged Host and asserts the body contains no `__NARUKAMI__`.

#### 3. Stats LAN listener serves your SPA directory before it checks auth — and the default directory contains the master token

`packages/backend/src/services/statsLan.ts:198` · **small** effort · **CONFIRMED** · dimension: `security`

**Why**  
Three findings from two dimensions collapse into one bug. (a) statsLan.ts:197-203 serves any file resolving under frontendDir — `fs.createReadStream(asset).pipe(res)` — BEFORE the `if (!authed) { send(401, ...) }` gate at line 206, on a listener bound at line 224 with `server.listen(port, '0.0.0.0', resolve)`; the module docstring at 16-19 claims it "404s everything else — no HTML". (b) frontend/api.ts:56 is `const TOKEN = injected?.token ?? (import.meta.env.VITE_RUNNER_TOKEN as string | undefined)`, and gen-token.mjs:31 writes that env var with the SAME secret config.ts:33-34 authenticates against — the verifier grepped the built artifact and found `Fs=(Wn==null?void 0:Wn.token)??"4556d4ae…"` byte-identical to .runner-token in BOTH packages/frontend/dist/assets/index-*.js and packages/desktop/release/win-unpacked/resources/frontend. The default frontendDir (routes/statsLan.ts:11-17) IS that dist, so no attacker-chosen path is needed. (c) routes/statsLan.ts:31-33 additionally passes `body.frontendDir` and `body.port` through unvalidated, turning it into a general unauthenticated file server for any directory containing an index.html. The existing test that claims to cover this (statsLan.test.ts:135-144, "exposes NOTHING but stats") calls startStatsLan(PORT) with no frontendDir, so spaIndex is null and the entire branch is dead during the test. Runtime-proved with a decoy dir: GET / → 401, GET /.env → 200.

**What to do**  
Three parts, all small. (1) Guard the token fallback with `import.meta.env.DEV` so `vite build` tree-shakes it out, and add a build-time assertion that no emitted asset contains the contents of .runner-token. (2) Stop honouring body.frontendDir; validate port as an integer in [1024,65535]. (3) Move the 401 above the asset branch — but not naively: the SPA's `<script src>` and Monaco's lazy `import()` carry no Authorization header, so first set a `Set-Cookie: nk_stats=<token>; HttpOnly; SameSite=Lax` on the authed `/` response (statsLan.ts:193) and extend the `authed` computation at 178-179 to accept it. Then change statsLan.test.ts:108 to pass a fixture dir and assert a tokenless asset GET is 401.

### Tier 2 — High value  <sub>(11)</sub>

_Real pain or real risk, good return on the effort._

#### 4. RunLog replay is unbounded on three routes — 1.39 MB in one WS frame, measured

`packages/backend/src/ws.ts:332` · **small** effort · **CONFIRMED** · dimension: `performance`

**Why**  
ws.ts:321-333 does `include: { logs: { orderBy: { ts: 'asc' } } }` with no take and no byte budget, then `run.logs.map(l => l.chunk).join('')` into a single send. I measured your live DB: the largest dockOpen run is 3,155 rows / 1,390,804 bytes, the largest run overall 2.3 MB, total RunLog 11,607 rows / 5.1 MB — every byte of the pinned one is materialized as Prisma objects, joined, JSON.stringify'd and pushed as ONE frame on restore. The identical bug exists twice more: terminals.ts:90-97 (the dead-run branch of GET /api/terminals/:id/read, which is on the orchestration read path and can be hit repeatedly) loads everything just to return the last ~200 lines, and runs.ts:298-309 returns every log row — and TerminalTab.tsx:50 calls api.getRun on EVERY Claude tab mount, on every reconnect (:504) and in the UAC poll loop (:544), purely to read claudeSessionId. Note terminals.ts:82 already computes the right answer for the LIVE branch (`Math.max(64 * 1024, lines * 512)`) and runner.ts:119 caps the in-memory transcript at 2 M chars — the discipline exists, it just stops at the ORM. Retention currently masks this; fixing item 1 removes that mask.

**What to do**  
Bound all three. Query newest-first with a row/byte budget (`orderBy: { ts: 'desc' }, take: N`), accumulate until ~MAX_TRANSCRIPT_CHARS, reverse, and prefix `[earlier output truncated]` so truncation is visible; send it in a few chunks rather than one frame. Apply the same take to terminals.ts:90 and runs.ts:298. Cheapest high-value sub-fix: give GET /api/runs/:runId a `select` that omits logs entirely unless asked, since its hottest caller only wants a UUID.

#### 5. /api/workspace dumps every AppSetting row: your Anthropic API key plus ~51 KB of EOD digest cache

`packages/backend/src/routes/workspace.ts:24` · **trivial** effort · **CONFIRMED** · dimension: `security`

**Why**  
workspace.ts:24 is `const settingsRows = await prisma.appSetting.findMany();` — no key filter — parsed at 26-32 and returned at 48. aiProvider.ts:48 stores the AI config under AI_SETTING_KEY='aiProvider' in that same table with the raw apiKey (aiProvider.ts:191-195), while routes/settings.ts:10-19 explicitly asserts "The stored API key is never serialized — responses carry a masked preview only" and GET /api/settings/ai does mask it. /api/workspace bypasses that projection entirely; the auditor proved it by injecting into the real workspaceRoutes and getting `{"aiProvider":{"apiKey":"sk-ant-SECRET…"}}` back. Same query also ships the EOD digest cache: I measured your live DB — 15 `eodDigest:` rows totalling 51,092 bytes of markdown against a single 568-byte `ui` row, and the endpoint is called on boot (App.tsx:159), on every re-dock (App.tsx:446) and in every pop-out (Popout.tsx:19). Master-gated and loopback, so this is defence-in-depth rather than a new boundary — but every spawned Claude tab holds the master token via mcpConfig.ts:63, so a prompt-injected session exfiltrates your billing credential with one GET. There is no test for routes/workspace.ts at all.

**What to do**
